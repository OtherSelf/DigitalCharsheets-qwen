# I18n

How UI strings are stored, named and checked. The app currently has two flat
dictionaries: [`translations.en.ts`](../src/lib/translations.en.ts) and
[`translations.ru.ts`](../src/lib/translations.ru.ts), exposed through
`useTranslation()` / `t('key')`.

## Overview

- One flat key namespace, one key per user-visible string.
- Both languages must contain the same keys and non-empty values.
- Components must not hardcode user-visible text: use `t('key')` for JSX text,
  `placeholder`, `title`, `aria-label` and `alt`.
- Proper names (`D&D`, `Dark Heresy`, `Scintilla`), units (`pt`, `ft`) and
  symbol-only values are exceptions, not translation gaps.

## Key conventions

Domain-specific keys should keep a domain prefix. Existing examples:

| Prefix | Area |
| --- | --- |
| `auth*` | login, registration, recovery, session |
| `admin*` | `/admin` UI and API errors |
| `dnd*` | D&D 5e labels/data |
| `dh*` | Dark Heresy labels/data |
| `settings*` | `/settings` profile and display controls |
| `demo*` | guest landing and `/demo` |
| `export*` / `import*` | export/import UI |

Data tables (`rank*`, `bg*`, `quirk*`, `boon*`, `race*`, `class*`, …) are data
keys, not a separate domain namespace. Shared labels such as `notes`, `save`,
`cancel` stay unprefixed only when they are truly universal.

New keys go **next to the feature block they belong to**, not into a random
tail. Use a short comment banner when adding a new block. Do not rename existing
keys in the same change as a feature fix.

## Rules

1. Add the same key to both dictionaries.
2. Keep `{placeholders}` unchanged in every language.
3. Translate RU values; only proper names and technical values may match EN.
   The current allowlist is in `tests/unit/translations.test.ts`.
4. Do not mix Cyrillic and Latin inside one word.
5. Do not bypass `t()`: JSX text and `placeholder`/`title`/`aria-label`/`alt`
   are checked statically.
6. Remove dead keys when a feature is deleted; don't leave stale `migrate*`
   blocks.

## Tests

- [`tests/unit/translations.test.ts`](../tests/unit/translations.test.ts) —
  key parity, literal `t('key')` coverage, empty values, duplicate keys, mixed
  scripts, and RU values that accidentally equal EN.
- [`tests/unit/i18n-hardcoded.test.ts`](../tests/unit/i18n-hardcoded.test.ts) —
  scans `.tsx` for JSX text and `placeholder` / `title` / `aria-label` / `alt`
  that bypass `t()`.

Known limitation: dynamic keys (`t(variable)`, `HOME_WORLD_KEYS[...]`, template
keys) cannot be verified statically; they rely on the mapping objects and must
be reviewed manually. Orphan-key reports are noisy for the same reason, so they
are not a failing test.

## Grouping and future namespacing

The dictionaries are currently one flat object in rough feature order. A full
rename to nested/namespaced keys (`dnd.*`, `dh.*`, `admin.*`) would touch every
`t()` call and every key; that is a separate codemod-sized change, not something
to mix with translation fixes.

Recommended path:

1. Keep existing keys stable.
2. Group new keys by feature with section comments.
3. Use domain prefixes for new domain-specific keys.
4. If strict namespacing is needed later, do it as one codemod with a typed key
   map and run the translation tests before/after.
