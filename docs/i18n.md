# I18n

How UI strings are stored, named and checked. Dictionaries are split by layer
and merged at startup:

- the common layer — [`translations.en.ts`](../src/lib/i18n/translations.en.ts)
  and [`translations.ru.ts`](../src/lib/i18n/translations.ru.ts);
- game metadata — [`src/games/i18n`](../src/games/i18n);
- module dictionaries — [`src/games/<id>/i18n`](../src/games/dnd5e/i18n).
  Each DH edition owns its full dictionary; there is no shared DH layer.

[`src/lib/i18n/index.ts`](../src/lib/i18n/index.ts) merges them through the game
registry and exposes the result via `useTranslation()` / `t('key')`. A duplicate
key between layers is a startup error.

## Overview

- Keys are flat strings with a **domain prefix**: `common.dashboard`,
  `dnd.classFighter`, `dh1.homeWorld`, `admin.searchPlaceholder`.
- One key per user-visible string; both languages must contain the same keys
  and non-empty values.
- Components must not hardcode user-visible text: use `t('key')` for JSX text,
  `placeholder`, `title`, `aria-label` and `alt`.
- Proper names (`D&D`, `Dark Heresy`, `Scintilla`), units (`pt`, `ft`) and
  symbol-only values are exceptions, not translation gaps.

## Domains

| Domain | Area |
| --- | --- |
| `common.*` | shared dashboard, sheet labels, actions, fields |
| `auth.*` | login, registration, recovery, session |
| `admin.*` | `/admin` UI and API errors |
| `dnd.*` | D&D 5e sheet/form/data labels (module `dnd5e`) |
| `dh1.*` | all Dark Heresy 1e strings (module `dh1`) |
| `dh2.*` | all Dark Heresy 2e strings (module `dh2`; may diverge from `dh1.*`) |
| `games.*` | registry metadata, edition names, creation wizard |
| `settings.*` | `/settings` profile and display controls |
| `demo.*` | guest landing and `/demo` |
| `io.*` | export/import UI |

Examples:

```text
common.notes
dnd.classFighter
dh1.homeWorld
admin.searchPlaceholder
auth.passwordPlaceholder
io.exportSheet
```

Keys are physically grouped by domain with section comments. New keys go
**next to the feature block they belong to**, not into a random
tail. Use a short comment banner when adding a new block. Do not rename existing
keys in the same change as a feature fix.

## Module dictionaries

Game-specific strings live with the game module, not in the common layer:

```
src/games/i18n/{en,ru}.ts              registry metadata: games.dnd.*,
                                       games.step*, wizard labels
src/games/dnd5e/i18n/{en,ru}.ts        dnd.* + games.dnd5e.*
src/games/dh1/i18n/{en,ru}.ts          games.dh1.* + dh1.* (via core-*.ts)
src/games/dh2/i18n/{en,ru}.ts          games.dh2.* + dh2.* (via core-*.ts)
```

Each module exposes `i18n: { en, ru }` in its `src/games/<id>/index.ts`.
Adding a game/edition therefore means adding one module with its dictionaries
and one registry entry — the merge in `src/lib/i18n/index.ts` picks it up
automatically. DH1 and DH2 keys are disjoint (`dh1.*` vs `dh2.*`), so the two
editions may translate the same concept differently without collisions.

Rules for a new key:

1. Shared UI string → common layer (`common.*`, `auth.*`, `admin.*`, …).
2. Game-specific string → the module that owns that UI. If both DH editions
   need it, add it to **both** `dh1.*` and `dh2.*`; there is no shared DH
   dictionary, so the translations can diverge later.
3. Registry/edition metadata → `games.*` in the owning layer.
4. Add the same key to `en` and `ru` of the same file.

## Level 1 and remaining transition

Level 1 moved 1127 UI keys to dotted domain keys. The 55 DH divination/effect
sentences were then migrated to stable IDs and namespaced data keys:

- `divination: "mutationWithout"` → `dh.data.divination.mutationWithout`;
- `divinationEffect: "insanity2"` → `dh.data.divinationEffect.insanity2`.

Old character files and 2.0 exports are normalized by the plugin's
`normalize` (`src/games/<id>/normalize.ts`, called through
`src/lib/character-version.ts`); unknown custom text is preserved. So there are
no unprefixed UI/data keys left.

The transition **suffix fallback** in `language-context.tsx` was removed at
stage 3: `t()` now returns the key itself when it is missing, so every call site
must pass a full `namespace.key`. The dashboard card / header subtitle / compact
nav receive their keys from the plugin slots, which is why the plugin UI files
are the only place that know `dnd.*` / `dh1.*` / `dh2.*` data keys.

Plugin dictionaries are **JSON** (`src/games/<id>/i18n/en.json` and `ru.json`,
D13): the same flat key/value map as the core TS dictionary, keys namespaced
`<id>.*`. The host merges them from `i18n.generated.ts`, generated by
`npm run plugins:generate` from `plugin.json#i18n`; the core TS dictionaries
(`src/lib/i18n/translations.*.ts`) stay TS.

Do not add new unprefixed keys. The namespace test fails on new camelCase keys
without a domain, and `tests/unit/plugin-slots.test.ts` checks that bare keys are
no longer resolvable.

## Rules

1. Add the same key to both dictionaries.
2. Keep `{placeholders}` unchanged in every language.
3. Translate RU values; only proper names and technical values may match EN.
   The current allowlist is in `tests/unit/translations.test.ts`.
4. Do not mix Cyrillic and Latin inside one word.
5. Do not bypass `t()`: JSX text and `placeholder`/`title`/`aria-label`/`alt`
   are checked statically.
6. Remove dead keys when a feature is deleted; don't leave stale blocks.

## Tests

- [`tests/unit/translations.test.ts`](../tests/unit/translations.test.ts) —
  key parity across the merged dictionaries, per-module `en`/`ru` parity,
  literal `t('key')` coverage, namespaced keys, empty values, duplicates inside
  a file and between layers, mixed scripts, and RU values that accidentally
  equal EN.
- [`tests/unit/i18n-hardcoded.test.ts`](../tests/unit/i18n-hardcoded.test.ts) —
  scans `.tsx` under `src/app`, `src/components` and `src/games` for JSX text
  and `placeholder` / `title` / `aria-label` / `alt` that bypass `t()`.

Known limitation: dynamic keys (`t(variable)`, `HOME_WORLD_KEYS[...]`, template
keys) cannot be verified statically; they rely on the mapping objects and manual
review. Orphan-key reports are noisy for the same reason, so they are not a
failing test.

## Future namespacing
