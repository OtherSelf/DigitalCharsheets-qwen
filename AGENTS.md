# AGENTS.md

Правила работы с репозиторием для людей и LLM-агентов.
Приоритет: этот файл > docs/ > стиль соседнего кода.
Если правило противоречит задаче — остановись и спроси, не обходи молча.
Если код и правило расходятся — сначала выясни, что здесь канон: правило
описывает текущее устройство проекта, а не пожелание на будущее.

## 0. Что это за проект

Self-hosted Next.js (App Router) без БД: профили и листы персонажей — JSON
в data-dir (`DCS_DATA_DIR`, по умолчанию `./data`). Игровые системы —
плагины в `src/games/<id>/` с манифестом `plugin.json`; реестр и словари
(`registry.generated.ts`, `i18n.generated.ts`) генерируются из манифестов.
Подробности: docs/architecture.md, docs/data-storage.md, docs/plugin-sdk.md,
docs/game-modules.md.

## 1. Стоп-лист (требует явного согласия человека)

- Новая npm-зависимость или мажорное обновление существующей.
- Изменение схемы данных (schemaVersion) или формата экспорта.
- Удаление/переименование публичного API-эндпоинта.
- Массовое переформатирование файлов, не относящихся к задаче.
- Новое ослабление проверок: безусловный skip/xfail, `eslint-disable`,
  `any` в новом коде, `typescript.ignoreBuildErrors`, удаление эталонов.
- Любые правки внутри data/ (данные пользователя, не код).

Допустимые исключения (не требуют согласия, но требуют объяснения в коде):
условный skip сценария, которому нужен внешний стенд или фикстура;
`eslint-disable` с комментарием, почему правило неприменимо; `any` и
`GameModule<any>` на границе плагинов, где тип намеренно стирается; `any` в
тестах для заведомо невалидных данных. Существующий долг (`any` в секциях
листов и тестах, текстовые ответы API без `reason`) — не повод добавлять
новый.

## 2. Комментарии

- Без эмодзи. Разрешены ASCII, типографские стрелки (→, >=) и обычная
  типографика (—, «», …, ·, §, ×, ≠).
- Комментарий объясняет ПОЧЕМУ, а не пересказывает код.
  Плохо: `// увеличиваем счётчик`. Хорошо: `// Next 16 блокирует чужой Origin,
  поэтому HMR-хост нужно разрешить явно`.
- Запрещён пересказ истории изменений: «раньше было…», «было/стало»,
  «added/removed», «исправлено в этапе 4», номера задач-однодневок.
  Ссылки на этап/решение (D3, «этап 3», SDK v1) допустимы, если указывают на
  актуальный архитектурный контекст в docs/. Прежнее поведение упоминай только
  тогда, когда оно и есть причина ограничения (почему нельзя иначе) —
  например, защита от обрезанного JSON в `src/lib/fs-atomic.ts`.
- Крупные неочевидные блоки помечаются маркером `LANDMARK: ИМЯ` — якорь
  заголовком: UPPER_SNAKE_CASE или короткое имя блока
  (`LANDMARK: ADMIN PAGE (/admin)`, `LANDMARK: STALE-WRITE GUARD`).
  Маркер не заменяет обычный комментарий: строчные фразы вида
  `// LANDMARK: Clean up form state` не использовать. Парный
  `─── END ИМЯ ───` допустим в больших блоках. Переиспользуй существующие
  имена, новые плоди без необходимости.
- Язык комментариев: русский или английский, но в пределах одного файла —
  один язык. `translations.en.ts` — английские комментарии,
  `translations.ru.ts` — русские. Идентификаторы, пути, API-поля — всегда как
  есть; LANDMARK-имена не переводятся.
- Никаких закомментированных «запасных» кусков кода. Удаляй.
- TODO только с контекстом: `TODO(причина): что и когда`. Голые TODO запрещены.

## 3. Коммиты

Формат: Conventional Commits, subject по-русски.

    <type>(<scope>): <повелительный глагол, что сделать>

- type: feat | fix | refactor | test | docs | style | chore | perf | build
- scope: подсистема (games, plugins, dh, dnd5e, i18n, admin, auth, api, ui,
  header, export, forms, sheets, settings, deps, visual, deploy…)
- subject: <= 72 символов, без точки в конце, без эмодзи, строчная после `:`.
  Формулировка результата, а не процесса: «сделать место рождения
  неизменяемым», не «работа над формой».
- Тело (обязательно для нетривиальных изменений):
  1) что изменено — по пунктам, с путями файлов;
  2) почему — причина/симптом бага, а не пересказ диффа;
  3) проверка — реальные команды и их результат.
- Строка проверки только с фактически выполненным прогоном:
  `Проверки: npm run verify — exit 0 (unit 431, build, smoke 45/45); visual — зелёный.`
  Запрещено писать непроверенные цифры и «должно проходить».
- Один коммит = одно логическое изменение. Рефакторинг и поведение — раздельно.
- Без атрибуции ИИ (Co-authored-by: бот, «сгенерировано…»), если человек
  явно не попросил.

## 4. Верификация перед коммитом

Обязательно: `npm run verify` → `scripts/predeploy.sh`:
lockfile (`npm ci --dry-run`) → format → lint (+ границы и реестр плагинов) →
typecheck → unit → build → smoke на временном data-dir. Флаги скрипта —
`npm run verify -- --skip-build --skip-smoke` для быстрой перепроверки.

- При изменениях UI: `npm run test:visual:fast` (@fast), при изменении вёрстки —
  полный `npm run test:visual`; `npm run test:visual:changed` — только
  затронутые диффом сценарии.
- При изменениях плагинов: `npm run plugins:check`, `plugins:boundaries`,
  `plugins:conformance` (он же входит в unit-набор).
- Эталоны (PNG) обновляются только осознанно, отдельным коммитом
  `test(visual): обновить эталоны …` с объяснением, что изменилось визуально.
- Безусловный skip/xfail запрещён: чини тест или удаляй сценарий с
  обоснованием. Условный skip допустим с явной причиной в сообщении.
- Упавшую проверку нельзя «зеленить» подгонкой теста под баг.
- Тестовые данные — только временный каталог: `useTempDataDir()` в
  `beforeEach`, `removeDir(dataDir)` в `afterEach`. `tests/unit/fixtures/` —
  данные, `*.test.ts` — проверки; импортировать `src/` в фикстуру нельзя.
- Ошибку инжектим, а не ждём от ФС или сети (`vi.spyOn`, `--require`-фикстура):
  тест обязан быть зелёным на ext4, на 9p и в CI. Модуль, который патчит
  глобалы, гоняем в дочернем процессе (образец — `fs-rename-fallback.test.ts`).
- После правки визуальных эталонов запускайте
  `npx vitest run tests/unit/visual-naming.test.ts`: имена, сироты и
  обязательное покрытие стережёт он, а не документация.

## 5. Архитектурные инварианты

- Ядро не знает конкретных игр. Никаких `if (gameSystem === 'D&D')` в src/lib,
  src/components, src/context — только через манифест/capabilities плагина.
- Плагин зависит от хоста только через разрешённый список
  (`scripts/plugins/boundaries.json`): `@/games/plugin-host`,
  `@/games/plugin-api`, `@/games/types`, `@/games/shared/*`,
  `@/components/ui/*`, `@/lib/utils`, `@/lib/i18n`, `@/lib/form-validation` и
  внешние react/zod/radix/…. `next/navigation`, контексты, `@/app` и прочие
  `@/lib/*` плагину запрещены; `npm run plugins:boundaries` падает на новой
  зависимости. Список в конфиге — источник истины, не этот абзац.
- uid берётся из сессии, никогда из query/body. Проверка роли — только на
  сервере (requireAdmin), клиентская роль — лишь для отображения.
- Запись JSON: writeJsonAtomic. Мутации, которые меняют профиль и индекс
  логинов (создание аккаунта, смена логина), — только под withDataLock.
- Миграции схемы идемпотентны, пишут файл только при реальном изменении,
  более новую schemaVersion не трогают.
- Пользовательские строки — только через i18n: ядро —
  `src/lib/i18n/translations.{en,ru}.ts`, метаданные игр — `src/games/i18n`,
  плагин — `src/games/<id>/i18n/{en,ru}.json`. Обе локали, ключ с доменом.
  Хардкод строк, `t('key') || 'fallback'` и «виртуальные» домены ключей
  запрещены. Новые ошибки, которые показывает UI, несут машинный `reason`-код,
  а текст берётся из словаря (образец — `IMPORT_ERROR_I18N_KEYS` в
  `src/lib/export-utils.ts`). Уже существующие текстовые ответы API в том же
  диффе не переводим — это отдельная задача.

## 6. Документация

- Правила docs/README.md обязательны: английский, одна тема на файл,
  kebab-case, ссылка на код вместо больших вставок.
- Изменил поведение — обнови соответствующую страницу docs/ в том же изменении.
- Этапы, версии SDK и D-решения — часть актуального описания, их можно
  упоминать. Прогресс, статусы, аудиты и бэклог в docs/ не кладём.
- Секреты, реальные пароли/токены/данные пользователей — никогда.

## 7. Поведение агента

- Не выдумывай API, флаги и поля. Проверь по коду или docs/, либо спроси.
- Не расширяй задачу молча: нашёл проблему рядом — сообщи, не чини в том же диффе.
- Читай соседний код и следуй его стилю; переписывать «по-своему» нельзя.
- Не сообщай о выполнении того, что не запускал. Неизвестно — так и скажи.
- В отчёте: что изменено, что проверено (с выводом), что осталось/риски.

## 8. Кроссплатформенность

- Текст в репозитории — LF, все файлы — `100644`: `.gitattributes` и
  `.editorconfig` задают переводы строк, исполняемый бит не трекаем.
  Скрипты запускаются через `npm run …`, `bash scripts/…` или
  `node scripts/…`, а не через `./`.
- Не делай `chmod +x` отслеживаемым файлам: на Windows и сетевых шарах это
  даёт вечный mode-only diff `M` при совпадающем содержимом.
- Фантомные «изменения» в Windows-клоне проверяй через `git diff`: если
  отличие только в режиме/EOL — это шум checkout, лечится `git checkout -- .`.
